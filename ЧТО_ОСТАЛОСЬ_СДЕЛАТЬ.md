# План завершения проекта

Источник требований: `docs/SPECIFICATION.md`. Ниже перечислены известные незавершённые места и проверки. Этот список не заменяет полную матрицу FR-01…FR-38.

## 1. Сначала стабилизировать уже написанный код

1. Запустить `pytest -x -vv`, затем весь набор с coverage. В текущем прогоне есть ошибки; нельзя считать ядро проверенным.
2. Проверить транзакции FastAPI и аудит: зависимость `db()` держит транзакцию до завершения запроса, а middleware пишет аудит через другую сессию. На SQLite это может приводить к `database is locked`. Исправить границу commit/audit, добавить регрессионный тест.
3. Исправить путь миграции в `backend/migrations/versions/0001_initial.py`: текущий `parents[3] / 'schema.sql'` указывает не туда; SQL находится в `backend/schema.sql`. Затем выполнить миграции на чистом PostgreSQL 15.
4. Проверить `tools/maintain.py`: архивирование использует `SELECT *` и порядок колонок, нужны явные списки. Подключить обслуживание витрин к расписанию. В оперативном контуре сейчас обычная таблица событий; требуемое секционирование оперативных данных ещё не реализовано.
5. Проверить маршруты и отрицательные сценарии всех API. Добавить обработку транспортных ошибок ML-прокси в единый формат ошибок.
6. Проверить конфигурацию сохранённого `ml_mode` после перезапуска API и worker. Сейчас состояние процесса и запись в БД могут расходиться.
7. Персистентная идемпотентность провайдера, конкурентные запросы и перезапуск требуют проверки; у router сейчас ограниченный кэш в памяти, у шаблона файловая запись без межпроцессной блокировки.
8. Запустить ruff, исправить замечания. Добавить mypy, ESLint/Prettier, pre-commit и README модулей. `requirements.lock.txt` фиксирует текущую среду, но не имеет хешей и требует проверки переносимости на Linux.

## 2. Данные и интеграции

1. Генератор: есть малый набор и параметр large (120 объектов, 12 лет), но 120 объектов дают 1080 каналов; для «сотни объектов, тысячи каналов» увеличить большой пресет минимум до 240 объектов. Большой набор пока не сгенерирован и не проверен.
2. Проверить, что генератор действительно покрывает каждую требуемую причину ложной сработки, отказы, пропуски, выбросы, дрейф и плановые работы. Сейчас часть этих случаев обозначена только в исходной логике; нужна отдельная карточка генератора и тест распределений.
3. Заполнить `docs/ml_handoff/`: словарь данных, определения меток, карточка генератора, рекомендации временной валидации, model card, шаблон ML-раздела, чек-лист стыковки. Сами файлы ещё не подготовлены.
4. `backend/adapters.py` содержит GET/файловые адаптеры, но нет полной проводки получения данных от реальных источников через конфиг, планировщик и API. Нужны эмуляторы оборудования/ОДС/заявок, sync work orders и надёжный кэш погоды в БД.
5. Open-Meteo adapter написан, но фактический вызов и сохранение погодных данных в контекст не интегрированы. Проверить поля API по официальной документации. Прогнозы прошлой погоды не выдавать за известные заранее.
6. После потокового ingestion пока не ставится приоритетное задание для объекта в Redis. Добавить постановку после commit, идемпотентность обработки и проверку задержки ≤300 секунд.
7. Импорт XLSX/CSV нуждается в тестах реальных форматов всех справочников, пустых ячеек, кириллических заголовков и несовпадения схем. Типы оборудования/объектов пока представлены упрощённо через `Object.meta`.
8. Исправить плановые окна при массовом seed: сейчас импорт синтетики напрямую записывает `expected=False`; использовать ту же нормализацию, что и ingestion. Время доступности метаданных оборудования также требует учёта в ретроспективном контексте.

## 3. ML-контракт и провайдеры

1. Дополнить OpenAPI схемами health/models/jobs/errors и ответами 4xx/5xx. В `contracts/ml/examples` пока нет примеров. Проверить, что JSON Schema выражает все ограничения runtime-валидаторов.
2. Проверить валидацию UTC во всех вложенных датах, конечность чисел, размеры рядов/пакетов, пустые ответы, дубли и чужие идентификаторы.
3. Compliance Kit нужно расширить: пакет 50 объектов, таймауты, неподдержанные горизонты, конфликт request_id, неизвестные объекты для любого внешнего сервиса, ошибочные ответы, авторизация, обучение/активация/откат, долговечность jobs.
4. Отдельно запустить один и тот же kit для rules через HTTP-шаблон и для stub через HTTP. Текущая конфигурация тестов задаёт тестовый токен в conftest; для реального `--ml-url` нужно сохранить внешний токен, а не перезаписать его.
5. Асинхронные job endpoints шаблона есть, но backend HTTP-клиент не использует асинхронный путь для тяжёлых backtest. Перенести тяжёлые задачи в очередь, вернуть job id и статус, обеспечить восстановление после перезапуска.
6. Режим plugin использует entry points, но тестовый пакет и проверки ещё не сделаны. Политика ensemble сейчас только предупреждает о большом расхождении; сделать её конфигурируемой.
7. Проверить, что выбранная активная/теневая версия действительно используется predictor. В текущем STUB ответ всегда stub v1.0, файловый реестр сам по себе не меняет вычисления.
8. Межсервисный TLS в compose сейчас не реализован (ML_URL использует http внутри сети). Требование TLS для ML нужно выполнить и проверить сервисный токен/сертификат.
9. Правила пока упрощённые: сезонная норма берётся из окна ряда, health шум/дрейф нуждается в нормировке, длительность горизонта не меняет вероятность. Это надо обосновать или доработать. Значения маркируются rules, калибровка не заявляется.

## 4. Метрики и разметка — приоритет корректности

1. Привести `ml.label_windows` SQL, Python `label_window` и Parquet-экспорт к единому определению. Для intrusion_false_alarm нужна метка конкретной сработки alarm_ref, а не обычное будущее временное окно. Сейчас SQL/экспорт этого не учитывают полностью.
2. Считать отрицательные метки только на подтверждённом полном покрытии; проверять начало и конец интервала и дату поступления истины. Защитить от смешивания синтетических и реальных наборов.
3. Решение диспетчера сохраняется в decisions, но не создаёт верифицированную истину в `ml.labels_*`. Нужен отдельный процесс подтверждения аналитиком с корректным временем инцидента, а не автоматическое превращение решения в факт.
4. Выявить повторные оценки и перекрывающиеся горизонты. Уточнить знаменатель «ложные тревоги на объект в сутки»: сейчас учитываются дни точек прогнозов, а не всё фактическое время наблюдения.
5. Сверить Precision/Recall/F1/AP(PR-AUC)/Brier/lead-time на ручных примерах, включая одинаковые вероятности, отсутствие положительного класса и пустые периоды.
6. Проверить аналоги по типу объекта и схожим предвестникам; сейчас простой приоритет типа инцидента, объекта и месяца.

## 5. UI и сценарии диспетчера

1. Открыть работающий стенд в браузере, пройти пожар/подтопление до сохранения решения, проверить responsive и отсутствие console errors. Визуальная проверка ещё не выполнена.
2. Исправить фильтрацию журнала: `act()` после применения фильтра вызывает общий `load()` и перезаписывает отфильтрованные события. Автообновление должно сохранять фильтры и период.
3. «Журнал прогнозов» сейчас показывает latest=true. Добавить полноценную историю, диапазон дат, пагинацию, фильтры исхода и версии.
4. Карта: добавить кластеризацию и корректное скрытие объектов по фильтрам. На текущей карте без прогноза всё равно отображаются объекты.
5. Карточка прогноза загружает текущий контекст, а не контекст на as_of прогноза. Показывать исторический снимок, подписи факторов перевести на русский, добавить обработку ошибок загрузки и focus trap диалога.
6. В журнале событий пока номер канала вместо требуемого типа/иконки; добавить типы, фильтры в заголовках, сортировку и пагинацию.
7. Добавить отклонение рекомендации с причиной и календарь окон, просмотр истории ремонтов; проверить роли кнопок черновика/what-if/backtest.
8. Аналитика: добавить фильтры периода/типа/версии, статистику и сезонность, полноценное сравнение active/shadow, загрузку размеченных данных через UI.
9. Управление: добавить запуск обучения, журнал заданий, откат версии, пользователей/ролей, полный набор настроек раздела 10.6. Сейчас показаны режим, модели, пороги и аудит.
10. Дополнить дашборд фактическим графиком риска, ложными тревогами за 24 ч и здоровьем датчиков. Эти показатели ещё не реализованы полностью.
11. Проверить WCAG AA, клавиатуру, светлую/тёмную тему (тёмная пока отсутствует), пустые/ошибочные состояния, уведомления и подтверждение чтения. Существующий SSE уже написан, но не проверен end-to-end.
12. Убрать ненужные импорты, улучшить типы Row вместо широкого any, разнести большой App.tsx по компонентам, разделить пакет Recharts для уменьшения bundle.

## 6. Безопасность и инфраструктура

1. Проверить LDAP/AD на OpenLDAP с тестовыми пользователями, группами и доверенным TLS. Сейчас контейнер профиля ldap не настроен полноценным набором групп/учётных записей.
2. Все внешние записи запрещены; добавить HTTP-level тесты GET-only для каждого адаптера. Не считать это доказанным только отсутствием метода write.
3. Аудит должен включать безопасные параметры изменяющих операций и не включать пароли/токены/ПДн. Сейчас в middleware пишутся только query-параметры; SSE исключён из записи.
4. Уточнить политику demo/prod, запретить слабый/пустой пароль LDAP bind, постоянный JWT secret обязателен для нескольких процессов. Rate limiting сейчас локален процессу и требует Redis для нескольких инстансов.
5. Проверить CSV/XLSX formula injection в экспортируемых отчётах, XML exceptions, path traversal, конфликты идентификаторов, гонки импортов и ограничения размеров до чтения тела.
6. Установить и проверить безопасные заголовки, CSP, HTTPS cookies, HSTS для целевого домена; избежать внешних Google Fonts/OSM в закрытом контуре при необходимости.
7. Выполнить `pip-audit`/`npm audit`, обновить уязвимости с повторной проверкой. Реестр THIRD_PARTY ещё не составлен.
8. Сделать backup по расписанию, проверку восстановления и замер RTO, политику хранения, чистку временных отчётов и файловых job-cache.
9. Образы и зависимости сейчас не разделены на runtime/dev. Проверить Linux-сборку, непривилегированных пользователей, healthchecks и корректное ожидание старта worker.
10. Протестировать совместимость PostgreSQL 12+, целевой 15, Redis и полный `make up && make seed` на чистой машине за 15 минут.
