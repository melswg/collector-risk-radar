# Collector Risk Radar

Прототип поддержки диспетчера инженерных коллекторов для задачи №8 «Москоллектор». Основная интегрированная ветка — `develop`. Работает с демонстрационными и локально загруженными обезличенными данными; подключения к системам заказчика нет.

## Состояние на 29 сентября 2026

В `develop` есть FastAPI backend, React/TypeScript интерфейс для пяти ролей, SQLite для локального запуска, схема PostgreSQL и миграции, импорт журнала событий, аудит, решения диспетчера и комментарии к рекомендациям. В UI доступны карта, очередь прогнозов, журналы, схема техника и аналитика. Геометрия сети и камеры демонстрационные.

Для одной цели работает ML-путь: зарегистрированный паспорт канала и события
до `as_of` → 19 признаков → `incident_24h.cbm` → каналовый isotonic-калибратор →
сохранённый прогноз новой тревожной записи в часовом окне модели → карточка и
решение диспетчера. Источник в записи — `ml`. Это не прогноз подтверждённой
аварии и не отдельные вероятности пожара или подтопления. Прежние `rules` и
контрактный `stub` остаются отдельными режимами. Детали: [стык ML](docs/ML_INTEGRATION_HANDOFF.md).

Telegram-доставка чрезвычайных уведомлений реализована на backend (привязка аккаунта, очередь, повтор, `/telegram/*` и `/notification-delivery/*` API, бот-команды) и покрыта unit-тестами с подменённым Telegram Bot API — см. [раздел ниже](#telegram-уведомления). По умолчанию канал выключен (`TELEGRAM_NOTIFICATIONS_ENABLED=false`) и **не проверялся против реального бота** — для этого нужен собственный `TELEGRAM_BOT_TOKEN`. SMS и email остаются локальным черновиком в UI без серверной реализации; их серверный статус — `disabled`. Внутреннее уведомление в интерфейсе не подтверждает отправку наружу.

На интеграционной контрольной точке проверен синтетический сценарий; после
поступления архива заказчика дополнительно проверен реальный формат справочников
и журнала на одном канале. Проверены backend-тесты, 16
frontend-тестов, production-сборка, живой HTTP-проход ML-прогноза и решения,
открытие карточки в браузере. PostgreSQL, Redis, LDAP, нагрузка, точность на
реальных данных и внешняя доставка отдельно не приняты. Актуальные
доказательства и ограничения: [статус передачи](docs/HANDOFF_STATUS.md).

## Как запустить локально

Нужны Python 3 и Node.js/npm. Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt -r ml-заново/requirements-inference.txt
export DEMO_PASSWORD='<свой пароль длиной не менее 12 символов>'
python -m backend.seed
make local
```

В другом терминале:

```bash
cd frontend
npm ci
npm run dev
```

Обычная страница `/` обращается к API на `127.0.0.1:8000` через Vite proxy. Один и тот же `DEMO_PASSWORD` нужен при создании пользователей и входе; не храните его в репозитории. Настройки приведены в `.env.example`; для полноценного стенда используйте `make configure` и `make up`, но этот путь отдельно не принят на чистой машине. Не публикуйте локальные секреты из `.env`.

Для просмотра интерфейса без backend откройте `/demo.html`: роли `dispatcher`, `technician`, `manager`, `analyst`, `admin`, пароль `demo`. В этом режиме решения и настройки хранятся локально в браузере и не доказывают серверную интеграцию.

## Telegram-уведомления

Отдельный канал доставки чрезвычайных сообщений (`Record(kind='notification')` с вероятностью выше `notification_threshold`) через официальный Telegram Bot API. Реализация изолирована в `backend/notifications/` и не меняет существующую бизнес-логику прогнозов: недоступность Telegram никогда не блокирует создание события — доставка только ставится в очередь (`notification_deliveries`), а отправляет её либо администратор вручную, либо отдельный процесс.

**Проверено вживую** (29.09.2026, реальный бот `@collector_risk_radar_aletrs_bot`, реальный сотрудник `dispatcher`): привязка через `/start`, реальное сообщение получено в Telegram, автоматическая доставка фоновым `backend.telegram_bot` без ручного шага (событие поставлено в очередь → подобрано и отправлено поллером за ~2–6 секунд), идемпотентность подтверждена (повторная постановка того же события не создаёт дубль). При живой проверке найдены и исправлены два дефекта: время в сообщении показывалось как `UTC` вместо настроенного часового пояса (`Europe/Moscow`/МСК), и `httpx` при включённом INFO-логировании писал токен бота в лог открытым текстом (Telegram сама зашивает токен в URL запроса — это контракт их API, не наш выбор; исправлено фиксацией уровня логирования `httpx`/`httpcore` на `WARNING` внутри `backend/notifications/telegram.py`, независимо от логирования вызывающего процесса).

**Переменные окружения** (см. `.env.example`):

```env
TELEGRAM_NOTIFICATIONS_ENABLED=false
TELEGRAM_BOT_TOKEN=your_bot_token_here
TELEGRAM_BOT_USERNAME=collector_risk_radar_aletrs_bot
TELEGRAM_API_BASE_URL=https://api.telegram.org
TELEGRAM_WEBHOOK_SECRET=
APP_PUBLIC_URL=
```

Токен только в `.env`/секретах окружения, никогда в коде или Git. Без `TELEGRAM_NOTIFICATIONS_ENABLED=true` и непустого `TELEGRAM_BOT_TOKEN` канал остаётся `disabled` — так же, как email и sms.

**Запуск.** API отдаёт `/api/v1/telegram/webhook` для продакшен-режима (защищён заголовком `X-Telegram-Bot-Api-Secret-Token` при заданном `TELEGRAM_WEBHOOK_SECRET`; сам `setWebhook` в Telegram нужно вызвать отдельно, это не делается автоматически). Для локальной разработки — long polling в отдельном процессе, который также повторяет недоставленные уведомления:

```bash
python -m backend.telegram_bot
```

В Docker Compose это сервис `telegram-bot` за профилем `telegram` (`make up-telegram`), не запускается вместе с обычным `make up`.

**Привязка сотрудника.** В настройках уведомлений (значок колокольчика → «Telegram-бот») сотрудник запрашивает одноразовую ссылку (`POST /telegram/link/token`, срок 10 минут), переходит в Telegram и нажимает «Запустить» у `@collector_risk_radar_aletrs_bot`. Бэкенд связывает `username` (в т.ч. LDAP) с `chat_id`. Далее доступны команды бота:

- `/start <токен>` — привязка по ссылке;
- `/status` — статус привязки;
- `/unlink` — отвязать;
- `/help` — список команд.

Отключить уведомления, не отвязывая аккаунт, можно переключателем в том же разделе (`PUT /telegram/status`).

**Получатели и повторы.** Уведомление ставится в очередь для каждого сотрудника с включённой привязкой (идемпотентно, по `notification_id+username+channel`). Отправка — 3 попытки с задержкой 0/1/5 минут, затем статус `failed`; администратор видит очередь и состояние каналов на вкладке «Управление» (`/notification-delivery/status`, `/outbox`) и может отправить очередь или тестовое сообщение вручную (флаг `confirm_send`), там же — таблица привязки Telegram по сотрудникам.

**Тестирование:**

```bash
python -m pytest tests/test_telegram.py -q
```

Реальные сообщения в тестах не отправляются — Telegram Bot API подменяется заглушкой (`monkeypatch`).

**Troubleshooting:** канал `unconfigured` — включён, но нет ни одного сотрудника с активной привязкой; `disabled` — не включён на сервере или не задан токен; ошибка `429` от Telegram обрабатывается автоматически (переход в `retry`); при постоянной ошибке доставка переходит в `failed` и видна в очереди администратора с кодом и сообщением ошибки (без токена и персональных данных в логах).

**Чтобы уведомление реально дошло автоматически, нужны оба условия одновременно:**
1. Запущен `python -m backend.telegram_bot` (или настроен webhook) — без него доставки копятся в очереди со статусом `pending` и не уходят, пока администратор не отправит их вручную через `/notification-delivery/dispatch`.
2. Вероятность прогноза реально пересекла `notification_threshold` (0.75 по умолчанию) — это отдельная, уже существующая и не относящаяся к Telegram бизнес-логика ([services.py](backend/services.py), см. также [PLAN.md](PLAN.md) про `rules`-провайдер как некалиброванную базовую линию). При живой проверке демонстрационный сценарий `/demo/fire` на полном синтетическом датасете (`backend.seed`) дал `0.72` — ниже порога, уведомление не создалось; это ожидаемое поведение фильтра, не дефект Telegram-цепочки. Сама цепочка (получатели → очередь → отправка → статус) проверена отдельно тестовым событием с `probability=0.91` через уже существующие `queue_deliveries()`/`dispatch_pending()`, без изменения порога.
## Сквозной ML-пример

После `python -m backend.seed` войдите в основную страницу `/` как диспетчер,
откройте «Демонстрационные сценарии» и нажмите «ML: новая тревога · синтетика».
Приложение создаст **один явно синтетический** паспорт газового канала `990001`
у демонстрационного объекта, добавит события текущего и предыдущих часов,
вызовет настоящие веса и откроет сохранённую карточку. Для неё доступна форма
решения диспетчера. В `/demo.html` этот серверный путь недоступен.

Для своего зарегистрированного канала аналитик сохраняет паспорт через
`PUT /api/v1/sensors/{id}/ml-passport`, импортирует события через
`POST /api/v1/ingest/events`; диспетчер или аналитик вызывает
`POST /api/v1/predictions/ml-channel/run` с `channel_id` и необязательным
`as_of`. Прогноз и решения читаются существующими
`GET /api/v1/predictions/{id}` и `POST /api/v1/predictions/{id}/decision`.
Для `as_of` без зоны используется московское время. На точной границе часа
используется предыдущий завершённый час; в прочее время — текущий неполный.
Результат содержит `extra.forecast_from` и `valid_until`: это фактическое окно
модели, которая обучалась на событиях **после расчётного часа и до 24 часов от
его начала**, а не обязательно на ровно 24 часах от момента запроса. При
тревоге в расчётном часе или отсутствии в нём события прогноз отклоняется.
Качество вероятности для неполного живого часа ещё не проверено. Порог действия для
калиброванного онлайн-канала не установлен, поэтому `risk=unrated` и
автоматическая отправка уведомления не выполняется.

### Проверка на переданном архиве

Архив `archive-2026-09-29_17-45-09.zip` не хранится в репозитории. В нём есть
95 объектов без координат, 11 485 каналов, справочник состояний и пример журнала
за 01.08.2026. CSV объектов и каналов загружаются через
`POST /api/v1/import/files?kind=objects|channels`; канал получает паспорт с
`synthetic=false`. Объекты без координат остаются доступными по ID, но не
получают вымышленную точку на карте. Повторяемый HTTP-прогон во временной БД:

```bash
python -m tools.verify_customer_archive '/абсолютный/путь/archive-2026-09-29_17-45-09.zip' \
  --channel 230543 --as-of '2026-08-01T09:00:00+03:00'
```

Проверка импортирует оба полных справочника, события выбранного канала,
сохраняет ML-прогноз и решение диспетчера; временная БД удаляется после проверки,
а исходный архив не меняется. Проверка также сообщает пробелы и противоречия
справочника состояний. Годовые архивы 2019–2026 содержат 313 546 017 строк;
продуктовый импорт всего объёма и оценка качества модели на нём не выполнены.

Тот же набор данных отдельно проверен в настоящем интерфейсе: все 95 объектов
остаются без координат и без вымышленных точек на карте, карточка показывает
источник `ML · incident_24h`, окно прогноза и отсутствие порога, а решение
диспетчера сохраняется через форму. Подробности и ограничения:
[статус передачи](docs/HANDOFF_STATUS.md).
