# Collector Risk Radar

Прототип поддержки диспетчера инженерных коллекторов для задачи №8 «Москоллектор». Основная интегрированная ветка — `develop`. Это рабочий прототип с демонстрационными данными, а не подключение к системам заказчика.

## Состояние на 29 сентября 2026

В `develop` есть FastAPI backend, React/TypeScript интерфейс для пяти ролей, SQLite для локального запуска, схема PostgreSQL и миграции, импорт журнала событий, аудит, решения диспетчера и комментарии к рекомендациям. В UI доступны карта, очередь прогнозов, журналы, схема техника и аналитика. Геометрия сети и камеры демонстрационные.

Прогнозы текущего приложения получают источник `rules` либо контрактный `stub`. **Обученные модели пока не вызываются из backend.** В отдельной ветке `ml` есть офлайн CatBoost-модели и результаты, но нет согласованного онлайн-сервиса и полного набора входных данных. Семантика четырёх ML-выходов отличается от типов текущего API. Детали: [стык ML](docs/ML_INTEGRATION_HANDOFF.md).

Telegram-доставка чрезвычайных уведомлений реализована на backend (привязка аккаунта, очередь, повтор, `/telegram/*` и `/notification-delivery/*` API, бот-команды) и покрыта unit-тестами с подменённым Telegram Bot API — см. [раздел ниже](#telegram-уведомления). По умолчанию канал выключен (`TELEGRAM_NOTIFICATIONS_ENABLED=false`) и **не проверялся против реального бота** — для этого нужен собственный `TELEGRAM_BOT_TOKEN`. SMS и email остаются локальным черновиком в UI без серверной реализации; их серверный статус — `disabled`. Внутреннее уведомление в интерфейсе не подтверждает отправку наружу.

Последний проверенный код `develop` перед обновлением этих документов — `36703d6`. Проверены 30 backend-тестов, 16 frontend-тестов, production-сборка, локальный браузерный проход по пяти ролям и локальный API-сценарий вход → прогноз → решение → комментарий → статус каналов. PostgreSQL, Redis, LDAP, нагрузка, реальная доставка и сквозной ML-сценарий этим не проверены. Актуальные доказательства и ограничения: [статус передачи](docs/HANDOFF_STATUS.md).

## Как запустить локально

Нужны Python 3 и Node.js/npm. Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
make local
```

В другом терминале:

```bash
cd frontend
npm ci
npm run dev
```

Обычная страница `/` обращается к API на `127.0.0.1:8000` через Vite proxy. Для данных демо и пользователей запустите `python -m backend.seed` в активированном окружении. Настройки приведены в `.env.example`; для полноценного стенда используйте `make configure` и `make up`, но этот путь отдельно не принят на чистой машине. Не публикуйте локальные секреты из `.env`.

Для просмотра интерфейса без backend откройте `/demo.html`: роли `dispatcher`, `technician`, `manager`, `analyst`, `admin`, пароль `demo`. В этом режиме решения и настройки хранятся локально в браузере и не доказывают серверную интеграцию.

## Telegram-уведомления

Отдельный канал доставки чрезвычайных сообщений (`Record(kind='notification')` с вероятностью выше `notification_threshold`) через официальный Telegram Bot API. Реализация изолирована в `backend/notifications/` и не меняет существующую бизнес-логику прогнозов: недоступность Telegram никогда не блокирует создание события — доставка только ставится в очередь (`notification_deliveries`), а отправляет её либо администратор вручную, либо отдельный процесс.

**Переменные окружения** (см. `.env.example`):

```env
TELEGRAM_NOTIFICATIONS_ENABLED=false
TELEGRAM_BOT_TOKEN=your_bot_token_here
TELEGRAM_BOT_USERNAME=collector_risk_radar_aletrs_bot
TELEGRAM_API_BASE_URL=https://api.telegram.org
TELEGRAM_WEBHOOK_SECRET=
APP_PUBLIC_URL=
```

Токен только в `.env`/секретах окружения, никогда в коде или Git. Без `TELEGRAM_NOTIFICATIONS_ENABLED=true` и непустого `TELEGRAM_BOT_TOKEN` канал остаётся `disabled` — так же, как email и sms.

**Запуск.** API отдаёт `/api/v1/telegram/webhook` для продакшен-режима (защищён заголовком `X-Telegram-Bot-Api-Secret-Token` при заданном `TELEGRAM_WEBHOOK_SECRET`; сам `setWebhook` в Telegram нужно вызвать отдельно, это не делается автоматически). Для локальной разработки — long polling в отдельном процессе, который также повторяет недоставленные уведомления:

```bash
python -m backend.telegram_bot
```

В Docker Compose это сервис `telegram-bot` за профилем `telegram` (`make up-telegram`), не запускается вместе с обычным `make up`.

**Привязка сотрудника.** В настройках уведомлений (значок колокольчика → «Telegram-бот») сотрудник запрашивает одноразовую ссылку (`POST /telegram/link/token`, срок 10 минут), переходит в Telegram и нажимает «Запустить» у `@collector_risk_radar_aletrs_bot`. Бэкенд связывает `username` (в т.ч. LDAP) с `chat_id`. Далее доступны команды бота:

- `/start <токен>` — привязка по ссылке;
- `/status` — статус привязки;
- `/unlink` — отвязать;
- `/help` — список команд.

Отключить уведомления, не отвязывая аккаунт, можно переключателем в том же разделе (`PUT /telegram/status`).

**Получатели и повторы.** Уведомление ставится в очередь для каждого сотрудника с включённой привязкой (идемпотентно, по `notification_id+username+channel`). Отправка — 3 попытки с задержкой 0/1/5 минут, затем статус `failed`; администратор видит очередь и состояние каналов на вкладке «Управление» (`/notification-delivery/status`, `/outbox`) и может отправить очередь или тестовое сообщение вручную (флаг `confirm_send`), там же — таблица привязки Telegram по сотрудникам.

**Тестирование:**

```bash
python -m pytest tests/test_telegram.py -q
```

Реальные сообщения в тестах не отправляются — Telegram Bot API подменяется заглушкой (`monkeypatch`).

**Troubleshooting:** канал `unconfigured` — включён, но нет ни одного сотрудника с активной привязкой; `disabled` — не включён на сервере или не задан токен; ошибка `429` от Telegram обрабатывается автоматически (переход в `retry`); при постоянной ошибке доставка переходит в `failed` и видна в очереди администратора с кодом и сообщением ошибки (без токена и персональных данных в логах).
