# Collector Risk Radar

Прототип поддержки диспетчера инженерных коллекторов для задачи №8 «Москоллектор». Основная интегрированная ветка — `develop`. Работает с демонстрационными и локально загруженными обезличенными данными; подключения к системам заказчика нет.

## Состояние на 29 сентября 2026

В `develop` есть FastAPI backend, React/TypeScript интерфейс для пяти ролей, SQLite для локального запуска, схема PostgreSQL и миграции, импорт журнала событий, аудит, решения диспетчера и комментарии к рекомендациям. В UI доступны карта, очередь прогнозов, журналы, схема техника и аналитика. Геометрия сети и камеры демонстрационные.

Для одной цели работает ML-путь: зарегистрированный паспорт канала и события
до `as_of` → 19 признаков → `incident_24h.cbm` → каналовый isotonic-калибратор →
сохранённый прогноз новой тревожной записи в часовом окне модели → карточка и
решение диспетчера. Источник в записи — `ml`. Это не прогноз подтверждённой
аварии и не отдельные вероятности пожара или подтопления. Прежние `rules` и
контрактный `stub` остаются отдельными режимами. Детали: [стык ML](docs/ML_INTEGRATION_HANDOFF.md).

Telegram, SMS и email видны в настройках UI как локальный черновик. Серверный статус этих каналов — `disabled`, очередь отправки пуста; реальная доставка не реализована. Внутреннее уведомление в интерфейсе не подтверждает отправку наружу.

На интеграционной контрольной точке проверен синтетический сценарий; после
поступления архива заказчика дополнительно проверен реальный формат справочников
и журнала на одном канале. Проверены backend-тесты, 16
frontend-тестов, production-сборка, живой HTTP-проход ML-прогноза и решения,
открытие карточки в браузере. PostgreSQL, Redis, LDAP, нагрузка, точность на
реальных данных и внешняя доставка отдельно не приняты. Актуальные
доказательства и ограничения: [статус передачи](docs/HANDOFF_STATUS.md).

## Как запустить локально

Нужны Python 3 и Node.js/npm. Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt -r ml-заново/requirements-inference.txt
export DEMO_PASSWORD='<свой пароль длиной не менее 12 символов>'
python -m backend.seed
make local
```

В другом терминале:

```bash
cd frontend
npm ci
npm run dev
```

Обычная страница `/` обращается к API на `127.0.0.1:8000` через Vite proxy. Один и тот же `DEMO_PASSWORD` нужен при создании пользователей и входе; не храните его в репозитории. Настройки приведены в `.env.example`; для полноценного стенда используйте `make configure` и `make up`, но этот путь отдельно не принят на чистой машине. Не публикуйте локальные секреты из `.env`.

Для просмотра интерфейса без backend откройте `/demo.html`: роли `dispatcher`, `technician`, `manager`, `analyst`, `admin`, пароль `demo`. В этом режиме решения и настройки хранятся локально в браузере и не доказывают серверную интеграцию.

## Сквозной ML-пример

После `python -m backend.seed` войдите в основную страницу `/` как диспетчер,
откройте «Демонстрационные сценарии» и нажмите «ML: новая тревога · синтетика».
Приложение создаст **один явно синтетический** паспорт газового канала `990001`
у демонстрационного объекта, добавит события текущего и предыдущих часов,
вызовет настоящие веса и откроет сохранённую карточку. Для неё доступна форма
решения диспетчера. В `/demo.html` этот серверный путь недоступен.

Для своего зарегистрированного канала аналитик сохраняет паспорт через
`PUT /api/v1/sensors/{id}/ml-passport`, импортирует события через
`POST /api/v1/ingest/events`; диспетчер или аналитик вызывает
`POST /api/v1/predictions/ml-channel/run` с `channel_id` и необязательным
`as_of`. Прогноз и решения читаются существующими
`GET /api/v1/predictions/{id}` и `POST /api/v1/predictions/{id}/decision`.
Для `as_of` без зоны используется московское время. На точной границе часа
используется предыдущий завершённый час; в прочее время — текущий неполный.
Результат содержит `extra.forecast_from` и `valid_until`: это фактическое окно
модели, которая обучалась на событиях **после расчётного часа и до 24 часов от
его начала**, а не обязательно на ровно 24 часах от момента запроса. При
тревоге в расчётном часе или отсутствии в нём события прогноз отклоняется.
Качество вероятности для неполного живого часа ещё не проверено. Порог действия для
калиброванного онлайн-канала не установлен, поэтому `risk=unrated` и
автоматическая отправка уведомления не выполняется.

### Проверка на переданном архиве

Архив `archive-2026-09-29_17-45-09.zip` не хранится в репозитории. В нём есть
95 объектов без координат, 11 485 каналов, справочник состояний и пример журнала
за 01.08.2026. CSV объектов и каналов загружаются через
`POST /api/v1/import/files?kind=objects|channels`; канал получает паспорт с
`synthetic=false`. Объекты без координат остаются доступными по ID, но не
получают вымышленную точку на карте. Повторяемый HTTP-прогон во временной БД:

```bash
python -m tools.verify_customer_archive '/абсолютный/путь/archive-2026-09-29_17-45-09.zip' \
  --channel 230543 --as-of '2026-08-01T09:00:00+03:00'
```

Проверка импортирует оба полных справочника, события выбранного канала,
сохраняет ML-прогноз и решение диспетчера; временная БД удаляется после проверки,
а исходный архив не меняется. Проверка также сообщает пробелы и противоречия
справочника состояний. Годовые архивы 2019–2026 содержат 313 546 017 строк;
продуктовый импорт всего объёма и оценка качества модели на нём не выполнены.

Тот же набор данных отдельно проверен в настоящем интерфейсе: все 95 объектов
остаются без координат и без вымышленных точек на карте, карточка показывает
источник `ML · incident_24h`, окно прогноза и отсутствие порога, а решение
диспетчера сохраняется через форму. Подробности и ограничения:
[статус передачи](docs/HANDOFF_STATUS.md).
