# Коллекторский радар

Сервис поддержки диспетчера инженерных коллекторов для задачи №8 «Москоллектор» (ЛЦТ 2026). Результат для сдачи находится в ветке `premain`, рабочая интегрированная ветка — `develop`.

Сервис принимает события датчиков, считает вероятность новой тревожной записи по каналу на горизонте 24 часа, показывает объект, источник расчёта и окно прогноза, а решение о выезде или мониторинге принимает человек. Работает с демонстрационными и локально загруженными обезличенными данными; подключения к системам заказчика нет.

## Что уже реализовано

FastAPI backend с ролями и RBAC, аудитом действий, REST API, импортом справочников и журнала событий, схемой PostgreSQL и миграциями Alembic. React/TypeScript интерфейс для пяти ролей: карта объектов, очередь сигналов, карточка прогноза, решения диспетчера, журналы, аналитика и панель управления. Локально используется SQLite, для стенда предусмотрены PostgreSQL 15, Redis и Docker Compose.

ML-путь работает на настоящих весах: зарегистрированный паспорт канала и события до `as_of` дают 19 признаков, модель `incident_24h.cbm` и каналовый isotonic-калибратор возвращают сохранённый прогноз новой тревожной записи в часовом окне модели, который открывается карточкой и завершается решением диспетчера. Источник записи — `ml`. Это не прогноз подтверждённой аварии и не отдельные вероятности пожара или подтопления. Режимы `rules` и контрактный `stub` помечены отдельно и не выдаются за ML.

Telegram-доставка критических уведомлений реализована в `backend/notifications/`, покрыта unit-тестами с подменённым Bot API и проверена вживую 29.09.2026 на реальном боте: привязка через `/start`, реальная доставка сообщения, автоматическая отправка фоновым поллером за секунды, идемпотентность. Канал по умолчанию выключен (`TELEGRAM_NOTIFICATIONS_ENABLED=false`), SMS и email остаются локальным черновиком. Подробности — в разделе [Telegram-уведомления](#telegram-уведомления).

Документация: [описание решения](docs/SPECIFICATION.md), [допущения и ограничения](docs/ASSUMPTIONS.md), [сопроводительная документация](docs/Коллекторский_радар_сопроводительная_документация.docx).

## Как запустить локально

Нужны Python 3 и Node.js/npm. Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt -r ml-заново/requirements-inference.txt
export DEMO_PASSWORD='<свой пароль длиной не менее 12 символов>'
python -m backend.seed
make local
```

В другом терминале:

```bash
cd frontend
npm ci
npm run dev
```

Обычная страница `/` обращается к API на `127.0.0.1:8000` через Vite proxy. Один и тот же `DEMO_PASSWORD` нужен при создании пользователей и входе; не храните его в репозитории. Настройки приведены в `.env.example`; для полноценного стенда используйте `make configure` и `make up`, но этот путь отдельно не принят на чистой машине. Не публикуйте локальные секреты из `.env`.

Для просмотра интерфейса без backend откройте `/demo.html`: роли `dispatcher`, `technician`, `manager`, `analyst`, `admin`, пароль `demo`. В этом режиме решения и настройки хранятся локально в браузере и не доказывают серверную интеграцию.

## Сквозной ML-пример

После `python -m backend.seed` войдите в основную страницу `/` как диспетчер, откройте «Демонстрационные сценарии» и нажмите «ML: новая тревога · синтетика». Приложение создаст **один явно синтетический** паспорт газового канала `990001` у демонстрационного объекта, добавит события текущего и предыдущих часов, вызовет настоящие веса и откроет сохранённую карточку. Для неё доступна форма решения диспетчера. В `/demo.html` этот серверный путь недоступен.

Для своего зарегистрированного канала аналитик сохраняет паспорт через `PUT /api/v1/sensors/{id}/ml-passport`, импортирует события через `POST /api/v1/ingest/events`; диспетчер или аналитик вызывает `POST /api/v1/predictions/ml-channel/run` с `channel_id` и необязательным `as_of`. Прогноз и решения читаются существующими `GET /api/v1/predictions/{id}` и `POST /api/v1/predictions/{id}/decision`.

Для `as_of` без зоны используется московское время. На точной границе часа используется предыдущий завершённый час; в прочее время — текущий неполный. Результат содержит `extra.forecast_from` и `valid_until`: это фактическое окно модели, которая обучалась на событиях **после расчётного часа и до 24 часов от его начала**, а не обязательно на ровно 24 часах от момента запроса. При тревоге в расчётном часе или отсутствии в нём события прогноз отклоняется. Качество вероятности для неполного живого часа ещё не проверено. Порог действия для калиброванного онлайн-канала не установлен, поэтому `risk=unrated` и автоматическая отправка уведомления не выполняется.

## Проверка на переданных данных заказчика

Архив с данными не хранится в репозитории. В нём 95 объектов без координат, 11 485 каналов, справочник состояний и пример журнала за 01.08.2026; отдельно переданы восемь годовых архивов на 313 546 017 строк и часовая витрина `all_years_hourly.parquet`.

CSV объектов и каналов загружаются через `POST /api/v1/import/files?kind=objects|channels`; канал получает паспорт с `synthetic=false`. Объекты без координат остаются доступными по ID, но не получают вымышленную точку на карте. Повторяемый HTTP-прогон во временной БД:

```bash
python -m tools.verify_customer_archive '/абсолютный/путь/archive-2026-09-29_17-45-09.zip' \
  --channel 230543 --as-of '2026-08-01T09:00:00+03:00'
```

Проверка импортирует оба полных справочника, события выбранного канала, сохраняет ML-прогноз и решение диспетчера; временная БД удаляется после проверки, а исходный архив не меняется. Она также сообщает пробелы и противоречия справочника состояний.

Тот же набор данных проверен в настоящем интерфейсе: все 95 объектов остаются без координат и без вымышленных точек на карте, карточка показывает источник `ML · incident_24h`, окно прогноза и отсутствие порога, а решение диспетчера сохраняется через форму.

## Качество модели

Переданная часовая витрина закрыла отсутствующий шаг пайплайна: пересчёт калибровки воспроизводится и повторяет отгруженные числа до знака (2 079 638 спокойных часов 2025, Brier `0,012516` до и `0,012332` после isotonic, log loss `0,058031` и `0,0564`).

Оценка на 2026, который не участвовал ни в обучении, ни в калибровке: 1 145 342 спокойных часа, PR-AUC `0,284`, ROC-AUC `0,862`, Brier `0,02421` без калибровки и `0,024442` с калибратором 2025, log loss `0,102497` и `0,101322`. На уровне объект-дней, который видит диспетчер: Precision `0,723`, Recall `0,464`, F1 `0,566`.

Честные оговорки: перенос калибровки 2025 на новый год по Brier не подтверждён, эксплуатационный порог онлайн-канала не согласован, а разметка опирается на тревожную запись, а не на подтверждённый инцидент. Команды воспроизведения: `python ml-заново/backtest.py` и `python ml-заново/calibrate.py`; результаты — в `ml-заново/models/new_alarm_backtest_2026.json` и `ml-заново/models/new_alarm_calibration_metrics.json`.

## Telegram-уведомления

Отдельный канал доставки чрезвычайных сообщений (`Record(kind='notification')` с вероятностью выше `notification_threshold`) через официальный Telegram Bot API. Реализация изолирована в `backend/notifications/` и не меняет существующую бизнес-логику прогнозов: недоступность Telegram никогда не блокирует создание события — доставка только ставится в очередь (`notification_deliveries`), а отправляет её либо администратор вручную, либо отдельный процесс.

**Проверено вживую** (29.09.2026, реальный бот `@collector_risk_radar_aletrs_bot`, реальный сотрудник `dispatcher`): привязка через `/start`, реальное сообщение получено в Telegram, автоматическая доставка фоновым `backend.telegram_bot` без ручного шага (событие поставлено в очередь → подобрано и отправлено поллером за ~2–6 секунд), идемпотентность подтверждена (повторная постановка того же события не создаёт дубль). При живой проверке найдены и исправлены два дефекта: время в сообщении показывалось как `UTC` вместо настроенного часового пояса (`Europe/Moscow`/МСК), и `httpx` при включённом INFO-логировании писал токен бота в лог открытым текстом (Telegram сама зашивает токен в URL запроса — это контракт их API; исправлено фиксацией уровня логирования `httpx`/`httpcore` на `WARNING` внутри `backend/notifications/telegram.py`).

**Переменные окружения** (см. `.env.example`):

```env
TELEGRAM_NOTIFICATIONS_ENABLED=false
TELEGRAM_BOT_TOKEN=your_bot_token_here
TELEGRAM_BOT_USERNAME=collector_risk_radar_aletrs_bot
TELEGRAM_API_BASE_URL=https://api.telegram.org
TELEGRAM_WEBHOOK_SECRET=
APP_PUBLIC_URL=
```

Токен только в `.env`/секретах окружения, никогда в коде или Git. Без `TELEGRAM_NOTIFICATIONS_ENABLED=true` и непустого `TELEGRAM_BOT_TOKEN` канал остаётся `disabled` — так же, как email и sms.

**Запуск.** API отдаёт `/api/v1/telegram/webhook` для продакшен-режима (защищён заголовком `X-Telegram-Bot-Api-Secret-Token` при заданном `TELEGRAM_WEBHOOK_SECRET`; сам `setWebhook` в Telegram нужно вызвать отдельно, это не делается автоматически). Для локальной разработки — long polling в отдельном процессе, который также повторяет недоставленные уведомления:

```bash
python -m backend.telegram_bot
```

В Docker Compose это сервис `telegram-bot` за профилем `telegram` (`make up-telegram`), не запускается вместе с обычным `make up`.

**Привязка сотрудника.** В настройках уведомлений (значок колокольчика → «Telegram-бот») сотрудник запрашивает одноразовую ссылку (`POST /telegram/link/token`, срок 10 минут), переходит в Telegram и нажимает «Запустить» у `@collector_risk_radar_aletrs_bot`. Бэкенд связывает `username` (в т.ч. LDAP) с `chat_id`. Далее доступны команды бота: `/start <токен>` — привязка по ссылке, `/status` — статус привязки, `/unlink` — отвязать, `/help` — список команд. Отключить уведомления, не отвязывая аккаунт, можно переключателем в том же разделе (`PUT /telegram/status`).

**Получатели и повторы.** Уведомление ставится в очередь для каждого сотрудника с включённой привязкой (идемпотентно, по `notification_id+username+channel`). Отправка — 3 попытки с задержкой 0/1/5 минут, затем статус `failed`; администратор видит очередь и состояние каналов на вкладке «Управление» (`/notification-delivery/status`, `/outbox`) и может отправить очередь или тестовое сообщение вручную (флаг `confirm_send`), там же — таблица привязки Telegram по сотрудникам.

**Тестирование:** `python -m pytest tests/test_telegram.py -q`. Реальные сообщения в тестах не отправляются — Telegram Bot API подменяется заглушкой (`monkeypatch`).

**Troubleshooting:** канал `unconfigured` — включён, но нет ни одного сотрудника с активной привязкой; `disabled` — не включён на сервере или не задан токен; ошибка `429` от Telegram обрабатывается автоматически (переход в `retry`); при постоянной ошибке доставка переходит в `failed` и видна в очереди администратора с кодом и сообщением ошибки (без токена и персональных данных в логах).

**Чтобы уведомление дошло автоматически, нужны оба условия одновременно:** запущен `python -m backend.telegram_bot` (или настроен webhook), иначе доставки копятся в очереди со статусом `pending` до ручной отправки администратором; вероятность прогноза пересекла `notification_threshold` (0.75 по умолчанию) — это существующая бизнес-логика ([services.py](backend/services.py)). При живой проверке демонстрационный сценарий `/demo/fire` на полном синтетическом датасете (`backend.seed`) дал `0.72`, ниже порога, поэтому уведомление не создалось: это ожидаемое поведение фильтра, а не дефект Telegram-цепочки. Сама цепочка (получатели → очередь → отправка → статус) проверена отдельно тестовым событием с `probability=0.91` через существующие `queue_deliveries()`/`dispatch_pending()`, порог не менялся.
