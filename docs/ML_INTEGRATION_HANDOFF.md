# Стык backend и текущей ветки `ml`

Проверено на `develop` (`36703d6` до документационной точки) и ветке `ml` на `35ea992` по состоянию на 29.09. UX/UI уже в `develop`, но он показывает текущие типы backend; интеграции с обученными моделями от этого не появилось.
Пример запроса: `contracts/ml/available_data_request.json`. Объект `20`, имя,
вид и родитель взяты из `ml:для_команды/справочник_объектов_диспетчер.csv`.
Историческая витрина `ml:для_команды/models/predictions/test_predictions_2026.parquet`
связывает с ним каналы `120473`, `120475`, `120466` и называет их температурными.
Три показания этих каналов предоставлены участником ML в переписке; они не
совпадают с исторической карточкой объекта `5963` ниже. `type_id=12` и
`type_code=temperature` — локальное соответствие backend, а `tag` содержит
строковый ID объекта: настоящего тега в справочнике нет. Время строк переведено
в UTC с предположением `Europe/Moscow`; часовой пояс источника не подтверждён.
Одного показания на канал недостаточно для надёжной оценки или проверки модели.

| Выход модели `ml` | Тип backend | Состояние соответствия |
| --- | --- | --- |
| `fault`: отказ по значению «Неопределен» | `sensor_failure` | Близкий смысл, но определение события нужно согласовать. |
| `new_incident`: любой новый инцидент | `fire`, `flood` | Не разделяет пожар и подтопление. |
| `critical`: пожар, затопление **или газ** | `fire`, `flood` | Агрегат нельзя выдавать за вероятность каждого типа; для газа отдельного типа нет. |
| `false_alarm`: уже существующая тревога без подтверждения | `intrusion_false_alarm` | Не ограничен доступом; неприменим без текущей тревоги. |

Текущие модели принимают строку `канал × час` с 42–45 признаками
(`ml:для_команды/models/metrics/metrics.json`), а контракт backend передаёт
объект, числовые ряды, здоровье каналов и необязательный контекст. Для живого
вызова нужны исходные события, справочник каналов с `type_id`, преобразование
признаков, согласованная семантика выходов и сервис `/v1/predict` с проверяемым
`model.kind = ml`. Ветвь `ml` сейчас содержит веса, калибраторы, офлайн-витрины
и скрипты обучения, но не этот сервис; `model_tables/` и сырые логи отсутствуют.
Backend по умолчанию работает в `rules`, а контрактный `stub` возвращает
шаблонный ответ. Ни один из этих режимов не является работающим ML inference.

Участник ML прислал пример исходного журнала с полями `ид_события`,
`ид_канала_данных`, `дата`, `время`, `тревожное`, `значение_датчика`. Backend
принимает такой CSV: объединяет дату и время, сохраняет исходный флаг тревоги
и требует предварительно зарегистрированный канал. Числа хранятся в `value`;
текстовые состояния сохраняются в `raw`, а `value` остаётся `null`.
Связь каналов с объектом `20` подтверждена только исторической витриной,
а исходный справочник каналов для импорта всё ещё отсутствует. Текст не
подменяется числом и сам по себе не становится признаком
работающей ML-модели. Это проверка формата входа, не проверка ML inference.

Пример карточки, присланный участником ML, содержит объект `5963`, вероятность
`0.8424`, горизонт 24 часа и пять каналов. Это другой исторический пример,
не ответ на три строки журнала выше. Поле `факт_новая_тревога_в_24ч` — метка
последующей проверки; при живом прогнозе его ещё нельзя знать. Тип ML-головы,
запускаемый сервис и связка новых событий с этой карточкой не предоставлены.

Перед подключением новой работы в `ml` проверить её Git-изменения, один полный
вход/выход на доступных данных, определения четырёх прогнозов и контрактные
тесты. При отсутствии точного соответствия сохранить ML-головы как отдельные
типы после согласования контракта, не переименовывать вероятности механически.
