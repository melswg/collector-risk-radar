## 0. РОЛЬ И РЕЖИМ РАБОТЫ

Ты — команда из семи специалистов в одном лице:

1. Системный аналитик и архитектор (проектирует решение, ведёт трассируемость требований, отвечает за ML-контракт).
2. Backend-разработчик (Python).
3. Data-инженер (приём данных, хранилище, витрины, выгрузки датасетов; **не** ML-моделирование).
4. Frontend-разработчик (веб-интерфейс диспетчера).
5. DevOps-инженер (контейнеризация, развёртывание, резервное копирование).
6. QA-инженер (тесты, нагрузка, контрактные тесты ML-интеграции).
7. Технический писатель и презентатор (документация, питч).

**Задача:** спроектировать и написать **рабочий прототип** сервиса, который запускается одной командой, показывается жюри и сдаётся по требованиям раздела 13. Прогнозирующая часть в прототипе обеспечивается **сменным провайдером прогнозов**: сначала это rule-based провайдер (пишешь ты), затем — ML-сервис другого участника, подключаемый без изменения кода бэкенда и фронтенда.

**Принципы работы:**

- Полный код без заглушек в логике: запрещены `TODO`, `pass` вместо логики, `...`, «остальное по аналогии». Если файл нужен — он выдаётся целиком. (Исключение — заранее оговорённые точки расширения ML в шаблоне ML-сервиса, раздел 5.8: там заглушка допустима и обязана быть явно помечена.)
- Сначала работающий минимум (P0), затем расширения (P1, P2).
- Решения, не определённые в ТЗ, принимай сам и **записывай в реестр допущений** (этап 0); не блокируй работу вопросами. Вопросы — только если без ответа нельзя продолжить (не более 3 за раз).
- Если ты не можешь запускать код, **прямо пиши, что код не запускался**, и давай точные команды проверки. Запрещено утверждать, что тесты «прошли», если ты их не выполнял.
- Язык: интерфейс, документация, комментарии — **русский**; идентификаторы в коде, имена таблиц, эндпоинтов, коммиты — **английский**.

## 1. КОНТЕКСТ ЗАДАЧИ

**Заказчик:** Департамент жилищно-коммунального хозяйства г. Москвы; эксплуатирующая организация — АО «Москоллектор».
**Инфраструктура:** 825 км коллекторов; 19,7 тыс. км кабелей связи; 8,3 тыс. км силовых кабелей; 1,9 тыс. км теплотрасс и водопроводных сетей.

**Текущие проблемы:** работа реактивная (реакция только после срабатывания датчиков); значительная доля тревог — ложные срабатывания, ведущие к ненужным выездам; ТО по фиксированным срокам без учёта фактического состояния.

**Что должен дать сервис:** заранее выявлять риски отказов и инцидентов, сокращать ложные выезды, оптимизировать ТО/ППР, повышать безопасность эксплуатации.

**Пользователи:** диспетчеры ОДС и эксплуатационных подразделений; технический персонал; руководители эксплуатационных подразделений; аналитик (верификация данных).

**Соответствие стратегиям:** Стратегия развития строительной отрасли и ЖКХ РФ до 2030 г.; Национальная стратегия развития ИИ; федеральный проект ИИ нацпроекта «Экономика данных».

## 2. ЦЕЛЬ И ГРАНИЦЫ РЕШЕНИЯ

**Цель:** сервис предиктивной аналитики для прогнозирования инцидентов и поддержки принятия решений при планировании ремонтных работ в инженерных коллекторах Москвы.

**Ключевые задачи сервиса:**

1. Прогнозирование отказов датчиков и инженерных систем до их возникновения.
2. Раннее выявление рисков пожаров и подтоплений.
3. Аналитическая поддержка верификации несанкционированного доступа (выявление ложных срабатываний).
4. Рекомендации по ТО/ППР на основе фактического состояния оборудования.

**Сервис ДОЛЖЕН:** анализировать исторические и текущие данные мониторинга; обрабатывать журналы ОДС; работать с реестрами оборудования; выдавать прогноз **с вероятностью и временным горизонтом**; интегрироваться с существующими системами (только чтение); защищать данные.

**Сервис НЕ ДОЛЖЕН:** замещать диспетчеров; принимать окончательные решения об инцидентах; управлять оборудованием напрямую; проводить ремонтные работы. Итоговое решение всегда за человеком (human-in-the-loop) — это отражается и в архитектуре, и в интерфейсе.

**Архитектурный принцип ML-независимости.** Вся система (хранилище прогнозов, уведомления, дашборд, карта, журнал, решения диспетчеров, рекомендации, отчёты, оценка качества) работает с **абстрактным провайдером прогнозов**. Ни один модуль вне слоя `prediction_providers` не знает, чем получен прогноз: правилами, ML-сервисом или их комбинацией. Смена провайдера — конфигурация (`ML_MODE`), а не правка кода.

## 4. ДАННЫЕ

### 4.1. Источники

**Внутренние (только чтение, read-only):**

- **СМВУ:** данные датчиков — контактные, объёмные (движение), температурные, дымовые, газовые; near real-time.
- **Журналы ОДС:** записи о срабатываниях и история инцидентов; глубина — **не менее 12 лет**.
- **Реестр оборудования:** строительные конструкции (люки, вентшахты, камеры), электрооборудование (насосы, вентиляторы), датчики.
- **Система учёта заявок:** статусы плановых и аварийных работ.

**Внешние:**

- Метеослужбы через открытые API (по умолчанию Open-Meteo или аналог без ключа; за адаптером).
- Регламент технической эксплуатации коммуникационных коллекторов (РТЭК). **Текста РТЭК у тебя нет:** регламентные сроки вынеси в конфигурацию (YAML/БД), заполни примерными значениями с пометкой «условные, требуют сверки с РТЭК». Не выдавай выдуманные значения за нормативные.

### 4.2. Схема данных (из Приложения 1 к ТЗ)

См. Приложение A. Основные сущности: журнал сработок, реестр каналов, реестр типов каналов, дерево объектов и систем. Теги иерархические (`МК-1.1.1.1.1.1`): парсер иерархии делай конфигурируемым, из тега извлекай уровни (коллектор → участок → …) как атрибуты для группировки, карты и передачи провайдеру.

### 4.3. Особенности парсинга (обязательно)

- Числа с десятичной **запятой** (`25,00`); идентификаторы с **пробелами-разделителями** тысяч (`3 008 235 019`) — нормализовать.
- Даты `дд.мм.гггг чч:мм`; часовой пояс Europe/Moscow, в БД — UTC.
- Кодировки `utf-8`, `utf-8-sig`, `cp1251`; разделители `,` и `;`; автоопределение.
- XLSX: несколько листов, объединённые ячейки, строки-шапки.
- Дубликаты, пропуски, залипшие значения, выбросы — обрабатывать и логировать, не молча отбрасывать.
- Идемпотентный импорт (повторная загрузка файла не создаёт дублей).

### 4.4. Обезличивание

Обфускация выполняется **на стороне источника**. Сервис не хранит персональных данных; на входе — проверка (FR-07): эвристики ФИО, телефонов, e-mail, паспортных данных; режим «отклонить / пометить». Соответствие 149-ФЗ и 152-ФЗ описать в документации.

### 4.5. Синтетические данные (критично, в том числе для ML-разработчика)

Реальных данных у команды нет, поэтому **напиши воспроизводимый генератор синтетических данных** (`tools/synth/`), совместимый по формату с Приложением A:

- 12 лет истории (настраивается; пресет для быстрого старта — 1–2 года), сотни объектов, тысячи каналов;
- типы каналов 2–9 и 12; суточная и сезонная динамика температуры, реалистичный шум;
- **инциденты с известной «истиной»** (пожар, подтопление, проникновение) с предвестниками: рост температуры и дыма до пожара; учащение включения насосов, потеря фазы и ливень перед подтоплением; серия движений/контактов ночью перед проникновением;
- **ложные срабатывания** (заметная доля тревог): залипание датчика, помехи, плановые работы, животные, конденсат;
- отказы датчиков с деградацией (дрейф, рост шума, потеря связи);
- плановые работы (заявки) с окнами времени, вызывающие «ожидаемые» сработки;
- журнал ОДС с решениями диспетчеров и причинами;
- метеоряд, согласованный с подтоплениями.

Обязательные свойства: несбалансированные классы (инциденты редки), дрейф распределений между годами, пропуски и грязь. Разметка «истины» хранится **отдельно** от признаков. Все датасеты, выгруженные генератором, содержат в манифесте `"synthetic": true`. Подготовь «карточку генератора»: какие закономерности заложены, чтобы ML-разработчик понимал границы применимости (но без раскрытия скрытых правил, превращающих задачу в тривиальную). **В документации и презентации явно указывать, что метрики получены на синтетических данных.**

**Приоритет:** генератор и первый датасет — **ранний этап** (этап 3), чтобы ML-разработчик мог начать работу параллельно.

### 4.6. Форматы и обмен

Файлы: CSV, XLSX, Parquet (для выгрузок ML). API: JSON, XML. СУБД: PostgreSQL 12+ (целевая 15+). Геоданные: GeoJSON, WKT.

### 4.7. Хранение (три контура)

1. **Оперативный** — свежие данные и активные прогнозы (секционирование по времени).
2. **Архивный** — исторические сырые данные (партиции по месяцам, политика хранения).
3. **Аналитические витрины** — агрегаты для UI и для ML (материализованные представления / таблицы), обновляются по расписанию.

Интеграции с внутренними системами Заказчика — **строго read-only**: в адаптерах нет операций записи во внешние системы; добавь тест, проверяющий это.

### 4.8. Витрины и разметка для ML (реализуешь ты)

Схема БД `ml` (представления/таблицы) и одноимённая выгрузка в Parquet. Только чтение, отдельная роль `ml_reader`.

| Объект | Содержание |
|---|---|
| `ml.objects` | объекты и оборудование: id, тег, иерархия, тип, координаты, год ввода, критичность |
| `ml.channel_agg_5m`, `ml.channel_agg_1h` | по каналу: min, max, mean, std, first, last, count, доля пропусков |
| `ml.alarms` | сработки: время, канал, тип, событие, флаг `expected` (в окне плановых работ), связка с ОДС |
| `ml.sensor_health` | ежечасные диагностические показатели датчиков (FR-15) |
| `ml.planned_works` | заявки и окна работ, статусы |
| `ml.weather` | наблюдения и прогнозы с меткой времени публикации (чтобы не допустить утечки будущего) |
| `ml.labels_incident` | подтверждённые инциденты: объект, тип (fire / flood / intrusion), `start_ts`, `end_ts`, источник (запись ОДС) |
| `ml.labels_false_alarm` | сработки, признанные ложными, с причиной из справочника |
| `ml.labels_sensor_failure` | подтверждённые отказы датчиков |
| `ml.decisions` | обратная связь диспетчеров: прогноз, решение, причина, время |
| `ml.label_windows` | готовое представление «на момент `as_of` произошёл ли инцидент типа T на объекте в течение горизонта H» — **единое определение метки** для ML и для модуля оценки бэкенда |

Манифест выгрузки `manifest.json`: версия схемы, период, число строк, контрольные суммы, часовой пояс (UTC), `synthetic`, seed генератора, версия ПО.

## 5. ИНТЕГРАЦИЯ С ML-МОДУЛЕМ

### 5.1. Принцип

ML — заменяемый провайдер за портом `PredictionProvider`. Режимы (`ML_MODE`, конфигурация окружения):

| Режим | Описание |
|---|---|
| `rules` (по умолчанию) | Rule-based провайдер, входит в бэкенд (5.4). Прототип полностью работает без ML |
| `http` | Обращение к внешнему ML-сервису по контракту (Приложение C) |
| `plugin` | Python-пакет провайдера, подключаемый в процесс бэкенда (для случаев, когда ML-разработчик отдаёт код библиотекой) |
| `ensemble` | `rules` + `http`; итоговый прогноз — модель, правила используются как контроль правдоподобия и запасной вариант (стратегия задаётся конфигурацией) |
| `shadow` | Активный провайдер + теневой (FR-29) |

Выбор режима — без пересборки. Провайдеры регистрируются по имени через реестр (entry points / фабрика).

### 5.2. Что реализует бэкенд

1. Порт `PredictionProvider` (абстрактный класс) с методами `predict(request) -> response`, `health()`, `list_models()`, `start_training(job_spec)`, `get_job(job_id)`, `activate(model_id)`. Методы обучения и активации опциональны (`NotSupported` для rules-провайдера).
2. **Сборщик контекста** (`ContextBuilder`): по объекту и моменту `as_of` формирует контекст запроса из хранилища: окна рядов каналов, состояние датчиков (здоровье), недавние сработки (с флагом `expected`), плановые работы, история ТО, метео (факт+прогноз), метаданные объекта. Размер окон — конфигурация.
3. **ML-клиент** (`HttpMlProvider`): таймауты, повторные попытки с экспоненциальной задержкой, идемпотентность по `request_id`, пакетирование, асинхронные задания для тяжёлых пересчётов, аутентификация сервисным токеном, TLS.
4. **Отказоустойчивость:** circuit breaker; при недоступности или невалидном ответе ML — автоматический fallback на `rules` с пометкой «деградированный режим» в API, интерфейсе и метриках; возврат на ML — автоматически после успешных проверок здоровья. Некорректные ответы (вероятность вне [0,1], неизвестный объект/тип, отсутствующие поля) — валидировать по схеме, отбрасывать с логированием, не роняя пайплайн.
5. **Планировщик прогнозов:** пакетный расчёт по расписанию (по умолчанию каждые 5 мин для активных объектов, реже для остальных), расчёт по запросу, приоритетная очередь для объектов с новыми сработками; неизменившиеся прогнозы не порождают дублей.
6. **Хранение прогнозов** с метаданными: `provider`, `model_id`, `model_version`, `model_kind` (`rules` / `ml`), `contract_version`, `data_sufficiency`, `explanation`, `as_of`, `generated_at`, `valid_until`, `role` (`active` / `shadow`).
7. **Уровни риска** считает бэкенд по настраиваемым порогам из вероятности (провайдер отдаёт вероятность, а не «цвет»).
8. **Выгрузка датасетов и обратной связи** (`/datasets/export`, `/feedback/export`) для обучения.
9. **Прокси управления моделями:** статус, список, запуск обучения, активация, откат — через контракт.
10. **Модуль оценки качества (FR-25):** не зависит от типа провайдера и работает по таблице прогнозов и `ml.label_windows`. Метрики считать на numpy (без тяжёлых ML-зависимостей).
11. **Единая настройка** порогов, горизонтов, периодов и политики fallback.

### 5.3. Контракт

Полное описание — Приложение C. Ключевые правила:

- Транспорт REST/JSON, схема OpenAPI 3.1 + JSON Schema, файлы в `contracts/ml/` (`openapi.yaml`, `predict_request.schema.json`, `predict_response.schema.json`, `train_job.schema.json`, примеры).
- Семантическое версионирование `contract_version`. В рамках мажорной версии допускаются только обратно совместимые добавления (новые опциональные поля). Бэкенд игнорирует неизвестные поля, ML-сервис обязан принимать неизвестные поля запроса.
- Изменение контракта — только через запись в `contracts/CHANGELOG.md` и обновление Compliance Kit; версия контракта фиксируется по итогам этапа 1 (**заморозка v1.0**), чтобы ML-разработчик мог работать параллельно.
- Два способа получать данные для ML: (а) контекст в теле запроса; (б) прямое чтение витрин `ml.*` под ролью `ml_reader` (для обучения и пакетных расчётов). Оба поддерживаются.

### 5.4. Rule-based провайдер (обязательно; не «пустышка»)

Детерминированный, объяснимый, конфигурируемый через `config/rules.yaml`, покрыт unit-тестами. Возвращает **вероятность** через сглаживающую функцию (например, логистическое преобразование взвешенной суммы нормированных индикаторов) с явной пометкой `model_kind: "rules"`, а не «псевдо-ML».

| Тип | Предвестники и правила (значения — параметры конфигурации) |
|---|---|
| Пожар | превышение температуры над сезонной нормой (робастный z-score по каналу), скорость роста температуры (наклон на окне), срабатывания дыма/газа, состояние вентиляторов, сработки без плановых работ |
| Подтопление | частота включения насосов относительно базовой для объекта, потеря фазы, осадки: фактические и прогнозные на горизонт, историческая склонность объекта (число подтоплений за N лет) |
| Ложное срабатывание / проникновение | сработка внутри окна плановых работ, серия повторов на одном датчике за короткое время, плохое здоровье датчика, отсутствие сопутствующих сработок соседних датчиков, время суток |
| Отказ датчика | флаги диагностики FR-15: залипание, потеря связи, дребезг, рост шума, дрейф относительно соседей |

Каждый прогноз содержит `explanation.top_factors` (какие правила и с каким вкладом сработали). Rule-based провайдер служит: (1) рабочим прогнозом до готовности ML; (2) **базовой линией сравнения** — модуль оценки показывает, насколько ML лучше правил; (3) запасным вариантом при сбое ML.

### 5.5. Честная маркировка

В UI у каждого прогноза отображается метка источника («Правила v…» или «Модель <id> v…»). Если активен `rules`, в шапке дашборда постоянно виден статус «Прогноз по правилам (ML-модель не подключена)». В деградированном режиме — предупреждающий баннер. В документации и презентации указывается, в каком режиме получены показанные результаты.

### 5.6. Теневой режим и сравнение

Прогнозы теневой модели сохраняются с `role=shadow`, не попадают в дашборд, карту и уведомления; доступны только администраторам/аналитикам на странице сравнения моделей (метрики FR-25 по `model_id` и роли, график сравнения, разница по конкретным объектам).

### 5.7. Обратная связь

Каждое решение диспетчера, результат отработки и итоговая истина (подтвердилось / ложное) записываются в `ml.decisions` и `ml.labels_*` и доступны для дообучения. Разметка принимается только от ролей с соответствующим правом; версия справочника причин фиксируется.

### 5.8. Шаблон ML-сервиса (`ml_service_template/`)

Готовый каркас, который ML-разработчик берёт и наполняет:

- FastAPI-приложение, реализующее **весь контракт**: `/v1/health`, `/v1/models`, `/v1/predict`, `/v1/predict/jobs`, `/v1/train/jobs`, `/v1/models/{id}/activate`;
- валидация запросов/ответов по схемам контракта;
- **единственные** места, которые нужно менять: `predictor.py` (метод `predict_batch`) и `trainer.py` (метод `train`) — в шаблоне они содержат явно помеченные заглушки, возвращающие корректные, но фиктивные ответы (`model_kind: "stub"`, вероятность из детерминированного хеша) и логируют предупреждение «STUB»;
- загрузка данных: примеры чтения витрин `ml.*` под `ml_reader` и чтения Parquet-выгрузок;
- простой файловый реестр версий моделей (`models/<id>/<version>/`, `metadata.json`);
- `Dockerfile`, `requirements.txt`, подключение в docker-compose под профилем `ml`;
- README для ML-разработчика: что менять, что нельзя менять (контракт), как запускать локально, как пройти Compliance Kit.

### 5.9. Compliance Kit (контрактные тесты)

Набор тестов `tests/contract/ml/`, запускаемый против **любого** ML-сервиса (`pytest --ml-url=...`): соответствие схемам, обязательные поля, диапазоны вероятностей, поддержка нескольких горизонтов, обработка неизвестных объектов, идемпотентность по `request_id`, таймаут на пакет из N объектов (≤ 300 с на объект, по умолчанию замеряется), поведение при пустых рядах и при недостатке данных (`data_sufficiency: "insufficient"`), асинхронные задания. Rule-based провайдер и шаблон ML-сервиса обязаны проходить те же тесты. Готовность ML-модуля к интеграции = зелёный Compliance Kit.

### 5.10. Пакет передачи для ML-разработчика (`docs/ml_handoff/`)

1. `README_ML.md`: цель, границы, что делает ML, что делает бэкенд, как подключиться, как пройти Compliance Kit.
2. Контракт `contracts/ml/` и его CHANGELOG.
3. Описание витрин `ml.*`, определение меток, манифест, словарь данных.
4. Первый синтетический датасет (малый пресет и большой) + карточка генератора.
5. Рекомендации по валидации (раздел 5.11) и шаблон model card.
6. Шаблон раздела «ML» для общей документации и слайдов.
7. Чек-лист стыковки (Приложение D).

### 5.11. Требования к самому ML-модулю (справка; реализует другой участник)

Это справочный список, который бэкенд использует для проектирования контракта и метрик, но **не реализует**:

- задачи: отказ датчика; пожар; подтопление; ложные срабатывания / проникновение; основной горизонт 24 ч (минимум по ТЗ), опционально 6 и 72 ч;
- разбиение только по времени, без утечки будущего (метео — с временем публикации);
- дисбаланс классов, порог под стоимостную матрицу (для критических инцидентов приоритет — Recall);
- метрики: Precision, Recall, F1, PR-AUC, Brier, калибровка, lead time;
- сравнение с rule-based базовой линией бэкенда;
- объяснимость (топ-факторы), пометка «недостаточно данных» вместо уверенного прогноза;
- inference одного объекта ≤ 300 с;
- model card и версионирование.

## 6. ДЕТЕРМИНИРОВАННАЯ АНАЛИТИКА НА СТОРОНЕ БЭКЕНДА (без ML)

### 6.1. Здоровье датчиков (FR-15)

Ежечасный (и по потоку — экспресс-проверка) расчёт по каналу: залипание (нулевая дисперсия за окно при ожидаемой динамике), потеря связи (доля пропусков, разрыв в потоке), дребезг (число переходов состояния за окно), уровень шума относительно нормы канала, дрейф относительно соседей и сезонной нормы. Результат: статус `ok / warning / critical`, числовые индикаторы, причина. Хранение — `ml.sensor_health`; показ в карточке датчика и объекта; передача провайдеру.

### 6.2. Плановые работы (FR-16)

Связывание сработок с окнами заявок (объект, время, статус «в работе»/«согласовано»). Сработки внутри окна помечаются `expected=true`, не порождают тревог, отображаются приглушённо в журнале событий и передаются провайдеру. Настраиваемый допуск по времени до/после окна.

### 6.3. Нормализация событий

Приведение сырых значений каналов к событиям для журнала технологических событий (Приложение 2): «Норма», «Предупреждение», «Обнаружено движение» и т. п. — по справочнику типов каналов и конфигурируемым пороговым правилам.

## 7. РЕКОМЕНДАЦИИ ПО ТО/ППР

Rule-based движок (значения — конфигурация):

- вход: риск-вероятности от провайдера (любого), здоровье датчиков, возраст оборудования, дата последнего ТО, регламентные сроки (условные значения из конфигурации), плановые работы и заявки, метеопрогноз, критичность объекта;
- выход: приоритет (скор по формуле с весами), рекомендуемое действие (проверка, замена, чистка, калибровка и т. п.), рекомендуемое окно проведения (не пересекать другие работы и неблагоприятную погоду), обоснование (факторы), ссылка на прогноз;
- сравнение с фиксированным графиком: какие плановые ТО можно отложить, какие провести раньше;
- статусы рекомендации: «новая / принята / отклонена (причина) / выполнена»; итоговое решение за человеком;
- P2: черновик заявки (FR-18).

Движок не должен зависеть от того, какой провайдер выдал риск; при смене провайдера рекомендации пересчитываются без изменения кода.

Отклоняться от стека можно только с обоснованием в реестре допущений.

- Наблюдаемость: структурные логи, `/health`, `/metrics` (Prometheus); метрики ML-интеграции (латентность вызовов, доля fallback, ошибки контракта).
- Резервное копирование БД по расписанию (скрипт и описание восстановления; RTO ≤ 4 ч).
- Структура репозитория (образец):

## 10. ПОЛЬЗОВАТЕЛЬСКИЙ ИНТЕРФЕЙС (UX/UI)

### 10.1. Принципы

- Веб-интерфейс, интуитивный путь пользователя; **каждый элемент решает конкретную задачу и присутствует, только если нужен**; логически связанные блоки расположены рядом.
- Режим дежурства: высокая читаемость, минимум кликов до решения, крупные индикаторы. Риск — **цвет + иконка + текст**.
- Chrome и Яндекс.Браузер; адаптивность до планшета; тёмная и светлая темы — по возможности.
- Интерфейс не завязан на конкретный тип провайдера: все данные прогноза берутся из единой модели, источник показывается меткой.

### 10.2. Экраны

1. **Дашборд:** карточки (активные прогнозы по уровням риска, ложные сработки за 24 ч, датчики в зоне риска, ближайшие рекомендуемые ТО), топ-N объектов по риску, график динамики риска, мини-карта, **статус источника прогнозов** (правила / ML / деградация).
2. **Карта:** объекты, кластеризация, подсветка проблемных зон, фильтры по типу инцидента и уровню риска, панель объекта.
3. **Карточка прогноза:** вероятность, горизонт, локация, тип, метка источника, объяснение (топ-факторы), график показаний, здоровье датчиков, плановые работы, аналоги, форма решения (действие + причина из справочника + комментарий), «что если».
4. **Журнал прогнозов:** реестр с фильтрами; результат отработки; экспорт.
5. **Журнал технологических событий** (Приложение 2): вкладка «Список событий», диапазон дат, «Автообновление», кнопка обновления, колонки «Время регистрации / Объект / Тип датчика / Событие датчика / Тип события», сортировка и фильтры в заголовках, подсветка предупреждений, приглушение «ожидаемых» сработок.
6. **Рекомендации по ТО/ППР:** список, приоритеты, обоснование, календарь окон работ.
7. **Аналитика и качество прогнозов:** статистика по типам инцидентов, сезонность, метрики FR-25, бэктест «прогноз против факта», сравнение моделей (rules vs ML, active vs shadow).
8. **Администрирование:** пользователи и роли, аудит, настройки, страница «ML-интеграция» (статус, версии, режим, кнопки обучения/активации/shadow, журнал заданий, доля fallback).

### 10.3. Уведомления

Всплывающее и постоянное (центр уведомлений) оповещение о критических прогнозах в реальном времени, переход в карточку; звук — включаемый; подтверждение прочтения; дедупликация.

### 10.4. Графики

Достоверность диаграмм оценивается по визуальной воспринимаемости и корректности отражения данных: подписанные оси и единицы, честные шкалы, легенда, отсутствие искажающих эффектов, обработка пустых состояний и загрузки.

### 10.5. Доступность

Контраст WCAG AA, управление с клавиатуры, осмысленные подписи, состояния ошибок и загрузки на всех экранах.

### 10.6. Настраиваемые параметры (FR-32)

Пороги вероятности по уровням риска и типам инцидентов; горизонт; размеры окон контекста; частота пересчёта; политика уведомлений; регламентные сроки ТО; веса критичности и правил rule-based провайдера; допуск по плановым работам; включение метеофакторов; период автообновления; часовой пояс; режим ML (`ML_MODE`) и политика fallback (только администратор).

## 11. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ И БЕЗОПАСНОСТЬ

**Производительность:**

- расчёт прогноза для одного объекта, включая сборку контекста и вызов провайдера, ≤ **300 с** (rules-провайдер — секунды);
- задержка обработки потока ≤ 300 с;
- не менее **20 одновременных пользователей** без деградации (нагрузочный тест Locust или k6 с отчётом; проверка при `ML_MODE=rules` и при `http` с шаблоном ML-сервиса);
- задержка ML-сервиса не должна блокировать интерфейс: прогнозы читаются из хранилища.

**Надёжность:** резервные копии; восстановление ≤ 4 ч; идемпотентная обработка потока; повторные попытки с backoff; деградация вместо падения при недоступности внешних источников, включая ML; доступность — по регламенту Заказчика.

**Безопасность:**

- TLS 1.2+ (nginx с самоподписанным сертификатом в docker-compose и инструкция); ML-сервис — по TLS и сервисному токену;
- LDAP/AD, RBAC, журналирование **всех** действий пользователей (кто, что, когда, с какими параметрами), включая запуск обучения и смену активной модели;
- политика паролей/сессий, защита OWASP Top 10, rate limiting, безопасные заголовки;
- интеграции с системами Заказчика — только чтение; роль `ml_reader` — только чтение витрин `ml.*`;
- секреты только через окружение; проверка зависимостей (`pip-audit`, `npm audit`).

**Совместимость:** серверная часть — Linux; PostgreSQL 12+; Chrome и Яндекс.Браузер.

**Нормативная база:** ФЗ № 149-ФЗ; ФЗ № 152-ФЗ; по возможности терминология и структура документации по комплексу стандартов на автоматизированные системы (ГОСТ 34).

## 16. ЗАПРЕТЫ

- Не обучать и не имитировать ML-модели: rule-based провайдер и заглушки шаблона — всегда с честной маркировкой `rules` / `stub`.
- Не выдавать метрики правил или синтетики за метрики ML или реальных данных.
- Не выдумывать нормы РТЭК без пометки «условно».
- Не устанавливать в образ бэкенда ML-библиотеки (scikit-learn, LightGBM, CatBoost, SHAP и т. п.).
- Не менять ML-контракт после заморозки v1.0 иначе чем обратно совместимо и с записью в CHANGELOG.
- Не использовать обфускацию, закрытые бинарные компоненты, неизвестные лицензии.
- Не добавлять функции управления оборудованием и запись во внешние системы.
- Не оставлять заглушки, `TODO`, сокращения кода (кроме помеченных точек расширения шаблона ML-сервиса).
- Не менять требования раздела 3 без записи в реестр допущений.

## ПРИЛОЖЕНИЕ B. Пользовательские сценарии из ТЗ

**Сценарий 1. Прогнозирование пожара.** Участники: диспетчер, аналитик. Предпосылки: накоплены данные об инцидентах; система интегрирована с датчиками и реестром плановых работ.

1. Анализ данных: сопоставление показаний (температура, задымление) с плановыми работами и историческими паттернами.
2. Формирование прогноза: при аномалиях — расчёт вероятности и предупреждение.
3. Уведомление на дашборд: вероятность, временной горизонт, локация.
4. Верификация: диспетчер анализирует данные, при необходимости — внешние источники (камеры).
5. Решение: «выезд бригады» или «ложное срабатывание» с причиной из справочника.
6. Завершение: решение сохраняется в журнале для анализа и дообучения.

**Сценарий 2. Прогнозирование подтопления.** Те же участники. Предпосылки: накоплены данные о подтоплениях; интеграция с датчиками и метеоданными.

1. Анализ: частота включения насосов + прогноз метеослужб + исторические паттерны.
2–3. Прогноз и уведомление (как в сценарии 1).
4. Верификация.
5. Решение: «направление бригады на проверку» или «мониторинг ситуации» с причиной из справочника.
6. Завершение: журнал → дообучение.

**Ожидаемый результат:** своевременное информирование о рисках; фиксация принятых мер; накопление данных для повышения точности прогнозов.

Обе цепочки обязаны работать в демо-режиме (FR-35) сначала на rule-based провайдере, затем на ML без правок кода.

## ПРИЛОЖЕНИЕ C. ML-КОНТРАКТ v1.0 (черновик для этапа 1)

На этапе 1 оформи это как OpenAPI 3.1 + JSON Schema, дополни, обоснуй изменения в CHANGELOG и заморозь.

**Эндпоинты ML-сервиса** (префикс `/v1`, авторизация — сервисный токен в заголовке):

| Метод и путь | Назначение |
|---|---|
| `GET /health` | состояние сервиса, версия контракта, готовность моделей |
| `GET /models` | список моделей: `id`, `version`, `incident_types`, `horizons_h`, `status` (`active` / `shadow` / `inactive`), `trained_at`, `metrics` (произвольный объект), `data_manifest_id` |
| `POST /predict` | синхронный прогноз для пакета объектов (до N, по умолчанию 50) |
| `POST /predict/jobs`, `GET /predict/jobs/{id}` | асинхронный пакетный прогноз/ретроспективный прогон |
| `POST /train/jobs`, `GET /train/jobs/{id}` | обучение: ссылка на выгрузку (`dataset_id` или период + `manifest`), параметры; статусы `queued / running / succeeded / failed`, лог, итоговые метрики |
| `POST /models/{id}/activate` | активация версии; `POST /models/{id}/shadow` — перевод в теневую |

**Правила:**

- `probability` ∈ [0, 1]; уровень риска определяет бэкенд по порогам.
- `data_sufficiency` ∈ `ok | insufficient`; при `insufficient` вероятность может отсутствовать, а бэкенд показывает «недостаточно данных» вместо прогноза.
- `incident_type` ∈ `fire | flood | intrusion_false_alarm | sensor_failure`. Для `intrusion_false_alarm` вероятность означает «сработка является ложной»; для объекта прогноз относится к последней сработке (в ответе можно указать `alarm_ref`).
- Ошибки по отдельным объектам возвращаются в `errors[]` (`object_id`, `code`, `message`), общий HTTP-статус при этом 200; HTTP 4xx/5xx — только для ошибок запроса/сервиса.
- Идемпотентность: повторный запрос с тем же `request_id` возвращает тот же результат.
- Все времена — ISO 8601 UTC.
- Идентификаторы объектов и каналов — строго из данных бэкенда; неизвестный объект → `errors[]`, не падение.
- `what_if` — необязательное переопределение части контекста (например, `{"weather.forecast.precip_mm_delta": 10}`); формат фиксируется в схеме.
