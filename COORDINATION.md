Короткий регламент на время хакатона. Источник требований — `REQUIREMENTS_CHECKLIST.md`; порядок работ — `PLAN.md`; фактический результат — код и проверки. GitHub Issues, Projects и PR можно использовать по желанию, но для этой команды они не обязательны.

Интерфейс и один синтетический каналовый ML-путь уже интегрированы. `ml` и `ml2` остаются отдельными источниками ML-материалов; `ml2` целиком не вливалась. Следующие стыки и границы проверок записаны в [статусе передачи](docs/HANDOFF_STATUS.md). После новой контрольной точки сверяйте HEAD.

## Перед началом задачи

Участник пишет в существующий командный чат одной строкой: что берёт, в какой ветке работает и какие файлы или общий интерфейс затронет. Агент может подготовить текст; отправляет его другим людям только по явному поручению. Другой участник не начинает одновременно менять те же файлы без короткого согласования. Разделение только по потокам «Разработка» и «МЛ»; задачи разработки не закреплены постоянно за конкретными людьми.

Агент читает `AGENTS.md`, соответствующий этап `PLAN.md` и пункты чек-листа; проверяет текущую ветку и незакоммиченные изменения. Если работа идёт параллельно или затрагивает общие файлы, использовать отдельную ветку или worktree. Для одиночной последовательной работы дополнительная ветка не обязательна.

## Где находится результат

- `develop` — рабочая интегрированная версия приложения и **единственное место, где отмечается общий чек-лист**.
- `ml` и `ml2` — исходные ML-материалы и эксперименты. Работа в этих ветках сама по себе не закрывает требование работающего сервиса: нужная модель должна быть подключена и проверена в `develop`. Один путь `new_alarm_24h` уже подключён.
- `main` — проверенная версия для сдачи. Переносить туда результат после сквозного сценария и проверки материалов.

Для подключённого `new_alarm_24h` проверяемый пример находится в `tests/fixtures/ml_channel_example.json`, а путь описан в [ML handoff](docs/ML_INTEGRATION_HANDOFF.md). `contracts/ml/` содержит прежний объектный контракт и пример доступного запроса; он не подменяет каналовый формат. Для следующих ML-выходов оба потока согласуют смысл, поля и тест перед подключением; отдельная процедура с PR для этого не требуется. Целиком переносить `ml` или `ml2` в `develop` без проверки структуры и данных не следует.

## После законченного изменения

1. Запустить подходящие тесты или воспроизвести ручной сценарий. Коммитить законченное изменение, а не каждый ответ агента.
2. Подготовить для командного чата короткую сводку: что сделано, ветка и коммит, что проверено, какие пункты чек-листа затронуты, что осталось или заблокировано. Отправляет участник либо агент по его явному поручению.
3. Агент, который **включил результат в `develop` и проверил его там**, в том же изменении ставит `[x]` у полностью выполненных пунктов `REQUIREMENTS_CHECKLIST.md` и рядом кратко записывает проверку и путь к реализации. Частично выполненные пункты остаются `[ ]`.
4. Если в работе были только файлы ветки `ml`, передать результат интегрирующему участнику; до проверки в `develop` чек-лист не менять.

Общий `log.md` после каждого ответа ИИ не вести: статусы и доказательства уже находятся в чек-листе, Git и короткой передаче в чат. PR полезен, когда нужен просмотр значительного изменения другим участником, но не является обязательным шагом для каждой задачи.
