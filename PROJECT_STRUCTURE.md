# Структура проекта

Срез: 25.09.2026. Этот документ разделяет фактическое содержимое веток и целевую структуру будущей `main`. Целевая структура не означает, что интеграция уже выполнена.

## Назначение веток

| Ветка | Проверенный коммит | Фактическое состояние |
| --- | --- | --- |
| `main` | `c208bd3` | Одна строка в `README.md`; интегрированного продукта нет. |
| `develop` | `0e8ea68` | Backend, frontend, правила прогнозирования, ML-контракт и шаблон ML-сервиса. |
| `ml` | `f9d11e6` | Офлайн-пайплайн CatBoost, веса, прогнозы и отчёт. HTTP-интеграции с `develop` нет. |

Таблица выше фиксирует исходные коммиты веток до публикации командных документов. Текущее состояние и наличие файлов проверять по Git; документы публикуются отдельным коммитом и не доказывают готовность приложения.

## Фактическая `develop`

```text
collector-risk-radar/
├── backend/
│   ├── api.py, auth.py, db.py, services.py    # REST API, доступ, БД, прогнозы и решения
│   ├── ingestion.py, adapters.py, context.py # импорт, внешние источники, контекст
│   ├── analytics.py, exports.py, seed.py     # диагностика, отчёты, демоданные
│   ├── prediction_providers/                # rules, HTTP-клиент, fallback
│   ├── migrations/, schema.sql              # миграции и SQL-витрины
│   └── worker.py, scheduler.py              # фоновые задания
├── frontend/                                 # React, TypeScript, Vite
│   └── src/App.tsx, MapView.tsx, api.ts, style.css
├── contracts/ml/                             # OpenAPI и JSON Schema обмена с ML
├── ml_service_template/                     # FastAPI-шаблон; predictor сейчас STUB
├── config/                                  # правила, причины, параметры
├── deploy/                                  # Dockerfile, Compose, nginx
├── tools/                                   # генератор синтетики, эмулятор, экспорт, обслуживание
├── tests/                                   # API, core, контракт, Locust
├── docs/                                    # спецификация, допущения, статус передачи
├── ИСХОДНИКИ_ЗАДАНИЯ/                      # PDF ТЗ, текст и шаблон презентации
├── ПРОВЕРКИ/                                # журналы предыдущих проверок
├── PLAN.md, STYLE.md, PROJECT_STRUCTURE.md # командные документы
├── REQUIREMENTS_CHECKLIST.md, COORDINATION.md # требования и координация
├── AGENTS.md                                # инструкции агентам
├── .codex/config.toml                       # проектный MCP-каталог
├── Makefile, alembic.ini, requirements*.txt, pyproject.toml
└── README.md                                # пока одна строка
```

Известный статус проверки `develop`: прежний запуск pytest — 8 пройдено, 4 упало из-за блокировки SQLite при аудите; Compose на PostgreSQL/Redis и браузерный сценарий целиком не проверены. Подробности — `docs/HANDOFF_STATUS.md` и `ЧТО_ОСТАЛОСЬ_СДЕЛАТЬ.md`.

## Фактическая `ml`

```text
collector-risk-radar/ [ветка ml]
└── для_команды/
    ├── README.md, ОТЧЁТ_ML.md     # запуск, метод, метрики и ограничения
    ├── Обучение.ipynb              # ноутбук с анализом и графиками
    ├── pipeline_config.py          # годы выборок и конфигурация четырёх целей
    ├── build_model_table.py        # построение почасовой таблицы признаков
    ├── train_models.py, train_catboost.py
    ├── aggregate_object_scores.py # агрегация канал → объект/день
    ├── справочник_объектов_диспетчер.csv
    ├── models/
    │   ├── weights/               # 4 CatBoost-модели и калибраторы
    │   ├── metrics/               # JSON-метрики, важность, примеры карточек
    │   └── predictions/           # Parquet-прогнозы 2025/2026
    └── models_nb/                 # прежний HGB-бейзлайн
```

В `ml` не включены сырые журналы, `model_tables/` и сервис онлайн-инференса. Повторное обучение по одному содержимому ветки невозможно. Ветка также содержит отслеживаемый `__pycache__`; его не переносить в целевую `main`.

## Целевая интегрированная `main`

После выполнения `PLAN.md` единая `main` должна иметь один корень и один контракт между сервисами:

```text
collector-risk-radar/
├── AGENTS.md, PLAN.md, STYLE.md, PROJECT_STRUCTURE.md
├── REQUIREMENTS_CHECKLIST.md, COORDINATION.md
├── README.md                      # единый запуск, режимы и ограничения
├── backend/                       # API, БД, роли, импорт, прогнозы и решения
├── frontend/                      # карта и рабочее место диспетчера
├── ml/
│   ├── service/                   # HTTP-инференс по contracts/ml
│   ├── training/                  # признаки, обучение, оценка, конфигурация
│   ├── models/                    # проверенные веса и метаданные версий
│   └── reports/                   # model card, метрики, ограничения
├── contracts/ml/                  # единственный версионируемый контракт
├── config/                        # общие конфигурации без секретов
├── deploy/                        # сборка и запуск всех сервисов
├── docs/                          # архитектура, матрица требований, инструкции, испытания
├── tests/                         # backend, ML, контрактные и сквозные проверки
├── tools/                         # генераторы, эмуляторы, сервисные команды
├── ИСХОДНИКИ_ЗАДАНИЯ/           # первичные материалы, отдельно от исполняемого кода
└── .codex/config.toml             # необязательная конфигурация MCP для Codex
```

`ml_service_template/` остаётся до появления реального сервиса; затем удалить или заменить его только вместе с проверкой всех ссылок и Compose. Не переносить `для_команды/` в `main` как отдельный параллельный проект. Данные обучения, секреты, виртуальные окружения, кэши и сборки не коммитить. Миграцию структуры выполнять после рабочего совместного HTTP-сценария, чтобы не смешивать её с отладкой контракта.

## Правила обновления документа

После каждого объединения веток обновлять таблицу фактического состояния и дерево затронутой ветки. Раздел целевой `main` менять только при принятом архитектурном решении. Не переносить будущие файлы в раздел фактических до их появления в Git.
